## 新发现问题（本次复核新识别或仍未修复）

- 🟡 **`cancel_delivery` 未对 `sales_contract_items` 加 `FOR UPDATE`，与 `create_delivery` / `update_delivery_actual` 并发时 `delivered_qty` 存在竞态**
  - 证据：`tools/db_writer.py:2053-2135` 中读取 `delivery_order_items` 时加了 `FOR UPDATE`（`2083-2088`），但随后 `UPDATE sales_contract_items SET delivered_qty = delivered_qty - %s`（`2094-2098`）前并未锁定对应合同行。而 `create_delivery`（`1784-1791`）和 `update_delivery_actual`（`1982-1989`）均通过 `JOIN ... FOR UPDATE` 锁定了 `sales_contract_items`。
  - 场景：A 线程作废某发货单（读到 `delivered_qty=100`），B 线程同时为同一合同行新增发货（读到 `delivered_qty=100` 并加 40 写 140）并先提交；A 线程再按旧值减 40 写 60，最终 `delivered_qty` 与业务事实不符。
  - 建议：在 `cancel_delivery` 读取 `delivery_order_items` 时 `JOIN sales_contract_items ... FOR UPDATE`，或先 `SELECT ... FOR UPDATE` 预锁合同行。

- 🔵 **发货单审计 `record_id` 仍指向明细表（原 🔵-16 遗留未修）**
  - 证据：`tools/db_writer.py:1894` 先 `_doc_insert` 头表，随后循环插入明细并执行 `UPDATE`（`1895-1900`），`tools/db_writer.py:1916` 的 `record_id = cur.lastrowid` 取的是最后一次 `INSERT`（即 `delivery_order_items`）的 id，而 `write_audit` 的 `table_name='delivery_orders'`。按 `(table_name, record_id)` 反查会定位到明细行。
  - 建议：`_doc_insert(cur, "delivery_orders", head_row)` 时立即取其返回值作为 `record_id`。

- 🔵 **收款累计口径两端仍不一致（原 🔵-15 遗留未修）**
  - 证据：`tools/db_writer.py:259-260` 录入端累计收款用 `r.status != 'cancelled'`（含 draft），`tools/local_validator.py:1254` 校验器用 `r.status = 'confirmed'`。一旦真实数据出现 draft 收款，录入端拦截与校验器结论会互相矛盾。
  - 建议：统一为「非 cancelled」。

- 🔵 **e2e 报告数量与代码实际 check 数不符**
  - 证据：`tests/demo_roleplay_test.py` 中实际 `check(` 调用 55 处（`grep -c 'check('`），但 `77ad901` commit message 与代码注释均声称 56/56。属于文档/口径小偏差，不影响功能，但排障时易造成误解。

- 🔵 **校验器启动输出仍硬编码 `[0/15]`（原 🔵-17 遗留未修）**
  - 证据：`tools/local_validator.py:1717` 打印 `[0/15]`，而 `CHECK_STEPS` 实际为 16 步。与函数注释「步号从 CHECK_STEPS 自动推导」不一致。
