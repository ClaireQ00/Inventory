## 新发现问题

本次复核未发现新的 🔴/🟡 级别问题。两条 🔵 级观察供后续参考：

- 🔵 **贷记单录入未强校验 `shipping_no` / `material_id` / `contract_no` 三角关系**
  - 证据：`tools/db_writer.py:201-212` 仅校验 `(contract_no, contract_item_no)` 存在、`material_id` 存在、`shipping_no` 存在，未校验该 `material_id` 是否真在该 `shipping_no` 的报关明细里，也未校验该合同行是否真与该报关单的发货明细对应。
  - 影响：前端 `CreditNoteEntry.tsx` 通过报关明细带出合同行，正常操作不会挂错；直调 API 可构造出 `shipping_no` 与 `contract_no` 不匹配的贷记单，导致 `check_credit_notes_balance` 等报表口径失真。
  - 建议：在 `validate_fields` 中增加“`shipping_no` + `material_id` 必须在 `shipping_record_items` 中”以及“`shipping_no` 关联的 `delivery_no` 必须包含该 `(contract_no, contract_item_no)`”的校验。

- 🔵 **附件上传仍累计缓冲到内存上限后才落盘**
  - 证据：`api/main.py:377-391` 分块读取后仍 `chunks.append(chunk)`，最终 `b"".join(chunks)`，10MB 以内全部在内存。
  - 影响：相对旧版“无上限整读”已有改善，但在并发大文件场景下仍是内存风险。
  - 建议：超阈值后改为边读边写入临时文件/对象存储，或至少限制并发上传数。
