### 重点审查清单（按优先级）

**A. 规则闸门与事务安全** —— `tools/db_writer.py`（2300+ 行，核心文件）
- `create_delivery`：超发拦截、低价先发货拦截+老板特批（`price_gap_approved`/`price_gap_reason`）、关行禁发——逻辑有没有绕得过去的路？同一发货单多行混合场景有没有部分提交的漏洞？
- `close_contract_item`：幂等、合同状态联动、>5% 复核标记——边界值（恰好 5%、quantity=0）对不对？
- `create_stock_in` / `create_stock_out`：库存加减和流水是否在同一个事务里？`_apply_inventory` 失败时会不会留下半拉子数据？
- 所有多表写：异常路径是否真的全回滚？`conn.rollback()` 有没有漏网的分支（比如 errors 在写入之后才 append 的情况）？

**B. API 安全** —— `api/main.py`
- 目前**没有任何鉴权**（已知、刻意，内网自用）——在这个前提下，还有哪些"哪怕内网也不该裸奔"的洞？（SQL 注入、路径穿越、文件上传大小/类型、审计字段伪造等）
- 所有 SQL 是否全部参数化？有没有字符串拼接 SQL 的地方？
- 附件上传 `/api/aux/materials/{aux_code}/attachments`：类型/大小/文件名处理安不安全？

**C. 校验覆盖盲区** —— `tools/local_validator.py` + `scripts/run_local_validation.sh`
- 16 步校验分别管什么？有没有"两个校验各自假设对方会查"的三不管地带？
- 快照漂移 WARN 的口径（快照 vs 主数据）会不会把真错误淹没在 WARN 里？

**D. 前后端一致性** —— `frontend/src/pages/*.tsx` vs `api/main.py` vs `tools/db_writer.py`
- 前端表单能填出来的值，后端校验有没有兜不住的组合？
- 错误提示是否可操作（用户看到报错知道下一步干嘛吗）？

**E. 文档与代码漂移**
- BUSINESS_RULES.md 写的规则，代码里有没有没实现或实现不一致的？逐条对 R1–R14。

### 已知的设计决策（别当 bug 报）

- **快照原则**：单据行保存开单时点的重量/体积/汇率快照，主数据修正不回改历史单据——这是刻意设计。
- **无登录/无权限**：内网自用，老板特批等机制靠"留痕+公示"而非权限拦截——已知局限，已预留审批设计。
- **CSV 双轨**：MySQL 为主，`data/csv/` 定期回写——不是混乱，是刻意的导出通道。
- **负库存不拦截**：先做后补的业务约定（WARN 不 ERROR）。
- **8501 Streamlit 原则只读**，少数状态操作（关行按钮）走 db_writer 规则层+审计——老板已批准这个例外。
